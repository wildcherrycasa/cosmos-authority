## What was different from the previous run (2026-09-06)

⚠ **The earlier run did not fail.** A relay described it as "used earlier but failed"; that is not what
happened. On 2026-09-06 the verifier ran on this phone and produced VALID on a real refusal, plus
`SIGNATURE_INVALID` on a flipped byte and `KEY_UNKNOWN` on a renamed kid, all in airplane mode. What
failed was **our own published install line** (`pip install cryptography` cannot work on Android), which
was then fixed.

The difference this time is scope: 2026-09-06 ran **only the Python verifier** against a receipt fetched
from a gist. This run puts the **entire product** on the phone — the Node server, the three calls, the
signing, and the offline verification — with nothing fetched from the internet at decision time.

## Payload

`core/`, `api/`, `verifier/`, `package.json` from master at `f3676f0`. Cosmos has zero runtime
dependencies, so no install step. Served from the workstation over `adb reverse tcp:8901 tcp:8901`,
because Termux has no storage permission and cannot read `/sdcard`.

⚠ **Not a clean-room test.** The payload was staged from this workstation, not installed from a registry.
A registry install is a different test and has not been done.

## What went wrong on the way — both mine, both recorded

1. **The first transfer produced `gzip: not gzip`.** My local file server never started: port 8899 was
   already held by another process (`EADDRINUSE`). I had "checked" the server with `curl -o /dev/null -w
   %{http_code}` and got **200 — from the other process**. A status code proved nothing about my server.
   The second attempt verified the **bytes**: served length equal to local length, and the first two
   bytes equal to `1f8b`, the gzip magic number.
2. **I reported a tarball size of 197121 bytes. It was 50221.** The first number came from an `ls -l`
   column that was not the size. Neither number mattered to the outcome; printing an unverified one does.

## Caveats that stop this being "ready for public"

- The signing key was **ephemeral** — no `COSMOS_RECEIPT_PRIVATE_KEY` was set, so the server generated a
  dev key. Every receipt above is genuinely signed and genuinely verifiable, and all of it dies with the
  process. A real deployment must persist a key before the first receipt.
- The payload was staged from a workstation, not installed from npm or PyPI. Neither package is published.
- `x402/`, `mcp/` and the test suite were not on the phone. The MCP wrapper and the x402 verifier are
  **untested on Android**.
- One device, one Android version, one Termux install.

## `net_rc=6` is the CONTROL, and it must fail

The line above the verification reads `net_rc=6`. That is not a defect and it is not tolerated — **it is
the assertion.** The command was:

```
curl -sS -m 6 https://pypi.org ; echo net_rc=$?
```

run **after** airplane mode was enabled, against a public host chosen because it is unrelated to Cosmos.
curl exit 6 is "could not resolve host". It proves the phone had no working DNS at that moment, so the
`VALID` printed immediately afterwards **cannot have fetched a key, a revocation list, or anything else**.
Offline verification is the entire product claim, and a claim with no control behind it is decoration.

**Read it this way when you re-run:**

| `net_rc` | meaning |
|---|---|
| **6** | correct. No DNS. The verification that follows is genuinely offline. |
| **0** | ⚠ **THE TEST IS VOID.** The phone still had network; airplane mode did not take. Do not accept the `VALID` that follows — it proves nothing about offline behaviour. Re-enable airplane mode and start again. |
| 7, 28 | connection refused or timeout. Weaker than 6 but still no route; acceptable, note which. |

So: a resolution failure on the phone is not merely *compatible* with "works as intended" — **without it,
"works as intended" is unproven.**
